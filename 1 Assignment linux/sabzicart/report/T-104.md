# Part B: The checkout incident

## Part B Question 1: Pages with 5xx errors
Command: grep -E '" 5[0-9][0-9] ' access.log | cut -d' ' -f7 | sort | uniq -c | sort -rn
Answer: /checkout 35, /api/orders 8, /api/stock 3 (total 46, matching the 5xx count from Part A). grep has to come first because cut would throw away the status field.

## Part B Question 2: Hour with the most 5xx errors
Command: grep -E '" 5[0-9][0-9] ' access.log | cut -d: -f2 | sort | uniq -c | sort -rn | head -5
Answer: Hour 13 (13:00 to 13:59) had 38 of the 46 errors. The rest are spread thinly over other hours (19: 2, 20/22/23: 1 each, and more below the top 5). So it was a sharp spike.

## Part B Question 3: /checkout in hour 13
Command: grep '2026:13:' access.log | grep ' /checkout ' | cut -d' ' -f9 | sort | uniq -c | sort -rn ; grep '2026:13:' access.log | grep ' /checkout ' | grep -cE '" 5[0-9][0-9] '
Answer: 48 /checkout requests in hour 13 (28 x 500, 5 x 502, 15 x 200). 33 of them failed (about 69%).

## Part B Question 4: Busiest hour
Command: cut -d: -f2 access.log | sort | uniq -c | sort -rn | head -5
Answer: Hour 20 was busiest (255 requests), then 21 (235), 13 (230), 19 (220), 14 (200). The error hour (13) is not the busiest. Hour 13 had normal traffic, so the failures were not caused by too many visitors. Something broke around 13:00 (for example a bad deployment or a failing service behind checkout).

## Part B Question 5: Application log (app.log)
Command: grep ' ERROR ' app.log | cut -d' ' -f6- | sort | uniq -c | sort -rn ; grep ' ERROR ' app.log | cut -d' ' -f2 | cut -d: -f1 | sort | uniq -c | sort -rn | head -5
Answer: 53 ERROR lines. Most common message: "Payment gateway timeout after 30s" (29), then "Database connection refused" (13), "Order could not be saved" (6), "Search index unavailable" (3), "Rider app returned HTTP 500" (2). Most errors happened in hour 13 (31 of 53), the same hour as the 5xx spike in access.log. Likely cause: the payment gateway stopped answering around 13:00, so /checkout failed with 500/502 after 30 seconds.

## Part B Question 6: Save the 5xx lines
Command: grep -E '" 5[0-9][0-9] ' access.log > ~/sabzicart/report/errors-5xx.txt ; wc -l ~/sabzicart/report/errors-5xx.txt
Answer: errors-5xx.txt has 46 lines. > creates or overwrites the file, so it was run from ~/sabzicart/logs/web where access.log exists.

# Part C: The night-time login attack

## Part C Question 1: IP with the most 401s
Command: grep '" 401 ' access.log | cut -d' ' -f1 | sort | uniq -c | sort -rn | head -5
Answer: 203.0.113.77 with 238 of the 258 responses with 401.

## Part C Question 2: Hours, page and method of that IP
Command: grep '^203.0.113.77 ' access.log | grep '" 401 ' | cut -d: -f2 | sort | uniq -c ; grep '^203.0.113.77 ' access.log | cut -d' ' -f6,7 | sort | uniq -c | sort -rn
Answer: Active only at hour 02 (123 failures) and hour 03 (115 failures). Every request was POST /login (238 requests).

## Part C Question 3: User agent
Command: grep '^203.0.113.77 ' access.log | cut -d'"' -f6 | sort | uniq -c | sort -rn
Answer: python-requests/2.31.0 (238 requests). This is a script, not a human, so it is a password-guessing attack.

## Part C Question 4: 401s from everyone else
Command: grep '" 401 ' access.log | grep -vc '^203.0.113.77 '
Answer: 20 (258 - 238). They are probably normal customers mistyping a password: one to four per IP.

# Part D: Bots, missing pages and big downloads

## Part D Question 1: Search-engine bots
Command: cut -d'"' -f6 access.log | grep -ic bot ; cut -d'"' -f6 access.log | grep -i bot | sort | uniq -c | sort -rn
Answer: 174 requests: Googlebot 63, bingbot 61, AhrefsBot 50. The user agent is cut out first so a path like /robots.txt cannot be counted by mistake.

## Part D Question 2: Missing pages (404)
Command: grep '" 404 ' access.log | cut -d' ' -f7 | sort | uniq -c | sort -rn
Answer: /favicon.ico 61, /old-menu.html 40, /wp-login.php 19 (total 120). /wp-login.php is the hacking probe: it is the WordPress login page and the site does not use WordPress. /favicon.ico is requested automatically by browsers, and /old-menu.html is probably an old link.

## Part D Question 3: Largest response
Command: sort -k10,10nr access.log | head -n 3 | cut -d' ' -f1,7,9,10 ; cut -d' ' -f7,10 access.log | sort -k2,2nr | uniq -c | head -3
Answer: The largest response was 2483117 bytes (about 2.4 MB): /downloads/catalog-2026.pdf, downloaded 20 times.

## Part D Question 4: /admin requests
Command: grep -c ' /admin' access.log ; grep ' /admin' access.log | cut -d' ' -f9 | sort | uniq -c ; grep -A3 'location /admin' nginx-sample.conf
Answer: 17 requests, all with status 403 (forbidden). The nginx config has "location /admin { deny all; }", which blocks everyone.

## Part E: What happened at SabziCart today?
Around 13:00 the payment gateway stopped answering: the app log shows 28 gateway timeouts in that hour, 38 of the day's 46 server errors happened then, and 33 of 48 checkout attempts failed. Traffic in that hour was normal (the busiest hour was 20:00), so it was not an overload. Between 02:00 and 03:00 a script (python-requests) from 203.0.113.77 sent 238 failed POST /login requests, a password-guessing attack, while all other visitors together caused only 20 failed logins. Compared with yesterday, requests grew by about 18% (2649 to 3134), but server errors rose from 12 to 46 and failed logins from 14 to 258. Bots (174 requests), a probe for /wp-login.php and 17 blocked /admin requests were also in the log.
